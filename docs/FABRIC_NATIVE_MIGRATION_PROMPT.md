### 2. 最终目标与严格定义

最终产物必须同时满足以下三个目标，缺一不可：

1. **Fabric 原生**：生产代码只依赖 Minecraft 原版、Fabric Loader 和必要的 Fabric API。优先使用 Minecraft 原版注册表、Codec、Data Component、SavedData、网络载荷、资源包/数据包及生命周期；原版没有稳定入口时使用 Fabric API；两者都不能表达所需行为时才使用范围最小且有注释和测试的 Mixin。
2. **彻底脱离 Forge/NeoForge 框架**：不得保留 Forge/NeoForge Gradle 插件、运行依赖、类、注解、事件总线、Capability/Attachment API、DeferredRegister/RegistryObject、配置框架、网络封装、数据生成框架、平台抽象层或为了模仿这些 API 而存在的兼容外壳。要审计语义和架构残留，不只是搜索 import。
3. **行为与存档兼容**：The Aether 原有玩法、内容、服务端逻辑、客户端表现、多人同步和可配置行为必须保持；原 Forge/NeoForge 版本产生的有效存档升级后必须尽可能无损加载，稳定标识符、方块、物品、实体、方块实体、维度、世界生成、玩家数据、附件/能力数据、容器内容、进度和配置语义不得静默丢失或错配。

“彻底脱离框架”不等于禁止识别旧格式。为了读取旧存档，可以在隔离的迁移模块中使用 Minecraft 原版 NBT、Codec、DataFix、SavedData 或必要的 Mixin 读取 `ForgeCaps`、`neoforge:attachments`、Curios 等旧键名；只能把它们当作数据格式字符串，绝不能重新引入 Forge/NeoForge/Curios 的代码或运行依赖。兼容读取器必须幂等、可测试，并在迁移成功后写入当前 Fabric 格式；不得删除未知第三方数据。

JEI、Jade 等纯 Fabric 版第三方集成可以作为可选的 `compileOnly`/软依赖保留，但 Aether 核心玩法不得依赖它们启动。任何移植层、跨加载器抽象或仅为了复刻 Forge API 形状而存在的库/本地 facade 都必须移除或改写。对每项保留的非核心依赖，在审计文件中说明用途、加载隔离和缺失时的行为。

### 3. 事实来源和等价性规则

不得凭记忆猜测原功能。按以下优先级建立证据链：

1. 当前分支的稳定资源 ID、序列化字段、数据包资源和已经验证的行为。
2. Git 历史中与当前代码祖先对应的官方 Forge/NeoForge 实现、官方 release tag 和 `upstream` 远端分支。
3. 同版本或最近可比版本的官方 Fabric 分支/tag，用于确认已有移植意图，但不能用它掩盖 Forge/NeoForge 功能缺失。
4. 自动化测试、旧存档 fixture、历史日志、发布说明及可复现的游戏内观察。

对每个高风险行为，都要在审计文件记录“旧实现证据 -> 当前实现 -> 差异 -> 迁移方案 -> 验证证据”。若版本 API 已变化，保持玩家可观察行为和持久化语义，不要求逐行照搬旧实现。发现旧实现本身存在明显 bug 时，默认先保持兼容；只有在审计文件说明影响和理由后才能修正，不能把无关玩法改动混入迁移。

### 5. 执行顺序

#### 阶段 A：建立基线并完成全项目审计

先做只读调查并写入审计文件，然后才能大规模修改代码：

1. 读取仓库约束、构建文件、`fabric.mod.json`、Mixin 配置、现有文档、当前 diff、最近迁移历史、所有 source set 和生成资源入口。
2. 识别本分支从哪个 Forge/NeoForge/Fabric 分支或 tag 演进而来，记录可比较的 commit/tag。不要盲目 `git fetch` 或切换当前工作树；优先读取已有 refs，确需获取新引用时不得改写本地工作。
3. 运行基线构建和可用测试，记录完整命令、退出码、失败阶段、关键错误及日志路径。基线失败也要继续审计并分类原因。
4. 使用结构化搜索列出直接残留和“伪原生”残留：包/import、注解、类名、事件 hook、注册封装、Capability/附件、配置、网络 context、Dist/环境分支、数据生成、Forge 条件资源、`mods.toml`、access transformer、依赖、仓库、生成缓存、旧命名和模仿 Forge API 的本地 facade。
5. 不能因为 `rg "net.minecraftforge|net.neoforged"` 为零就判定完成。检查每个本地抽象存在的理由，特别关注 `config/ModConfigSpec.java`、`event/hooks` 风格容器、注册辅助类、附件兼容层、网络上下文和跨平台命名。
6. 为下面第 6 节的每个审计域建立矩阵，并给出优先级和依赖关系。审计覆盖完成后立即进入阶段 B，不能停下来只汇报。

#### 阶段 B：按风险和依赖实施迁移

按“持久化/注册表 -> 服务端核心 -> 网络 -> 客户端 -> 可选集成 -> 清理”的依赖顺序分小批次迁移，除非审计证据证明另一顺序更安全。每个批次都遵循：

1. 在审计矩阵把目标行改为 `IN_PROGRESS`，写明范围和验收方法。
2. 读取对应旧实现和当前实现，先确定行为契约、稳定 ID 和保存格式。
3. 用 Minecraft/Fabric 原生实现替换，保持变更范围集中，不做无关重构。
4. 补充自动化测试、GameTest、测试夹具或可重复 smoke 步骤。修复根因，不通过删功能、吞异常、硬编码假成功或禁用 Mixin/数据来让构建变绿。
5. 运行与风险相称的编译和测试；失败则继续定位修复，不能把未经验证的行标为 `DONE`。
6. 同步更新审计矩阵、接力摘要和决策日志，再处理下一批。

优先完成能解除大量后续风险的共享边界，但不要建立新的跨平台抽象层。允许创建 Aether 自己的领域抽象，前提是它表达游戏概念而不是模拟 Forge/NeoForge API，并在审计中说明必要性。

#### 阶段 C：系统验证和收尾

所有矩阵行完成后进行全量回归、残留扫描、旧存档测试和真实运行环境测试。发现问题立即把对应项改为 `REGRESSION` 并回到阶段 B。只有满足第 9 节全部完成门槛时才能把总状态改为 `COMPLETE`。

如果 Minecraft 26.2 自身不支持从某个过旧 DataVersion 直接升级，必须区分“Minecraft 官方升级链限制”和“Aether 迁移缺陷”，记录已验证的中间升级路径；不能简单把责任归给游戏版本后宣布兼容。

### 8. 构建、测试和真实环境验证

根据仓库实际任务调整命令，但至少执行并记录：

```powershell
.\gradlew.bat clean build
.\gradlew.bat test
git diff --check
```

若某任务不存在，记录 Gradle 的实际可用任务和替代验证，不得伪造结果。对数据生成、GameTest、客户端和服务端使用仓库实际存在的 Loom 任务。

在指定 PCL2 环境做最终集成验证时：

- 先验证 Java 25、loader、Fabric API 和目标 jar 版本。
- 对原有 `mods`、配置、日志、世界和服务器文件做清单；不得删除或覆盖用户文件。
- 构建产物只部署到隔离的测试副本或在备份后替换同名测试 jar，避免同时加载多个 Aether jar。
- 核心独立验证只启用 Fabric API + Aether；随后再验证当前环境中的可选 Mod 组合，以区分核心问题和联动问题。
- 服务端必须到达可接受连接的稳定状态，并正常执行保存和停止；扫描完整日志中的 `ERROR`、`WARN`、异常、missing mapping/registry、Mixin failure 和 codec/datafix 错误。

- 所有长时间运行进程都要设置明确的成功信号、超时和优雅停止；不得留下后台 Java 进程。
- 将命令、构建 jar SHA-256、启用 Mod 清单、测试世界副本、退出码、关键日志路径和结论写入审计文件。

最低回归场景包括：新世界创建；旧世界升级；Aether 门创建和双向传送；已有/新生成地形与三类地牢；全部关键容器；Boss 战；常见生物、骑乘和投射物；装备/饰品效果；死亡/重生/跨维度/重连；多人追踪与同步；资源重载；天空、雾、HUD、GUI、声音和粒子；无 JEI/Jade/联动 Mod 的纯净启动。

### 9. 完成门槛

只有以下条件全部满足，才能在审计文件把总状态设为 `COMPLETE` 并向用户报告完成：

- 所有审计域都有逐项结论，不存在 `NOT_AUDITED`、`TODO`、`IN_PROGRESS` 或 `REGRESSION`。
- 没有未解决的高/中风险 `BLOCKED`；任何明确接受的低风险限制都有用户可见说明和证据。
- 生产构建图中没有 Forge/NeoForge/跨平台移植层；源码、资源和生成输出无活动框架残留。仅允许测试/文档/隔离迁移器中出现作为旧数据键名的文字，并逐项说明。
- 不存在只为保持 Forge/NeoForge 调用形状而保留的 facade；所有事件、注册、配置、网络、附件和数据生成路径均为 Minecraft/Fabric 原生实现。
- 核心功能在没有可选 Mod 时能构建并运行，客户端和 dedicated server 均通过。
- 功能等价矩阵全部有测试或可重复观察证据。
- 代表性的 Forge/NeoForge 旧存档副本成功升级、保存、重启，并通过结构化数据和游戏内验证；没有静默数据丢失、ID 错配或重复迁移。

如果任一门槛未满足，必须准确报告“迁移尚未完成”，继续处理能够推进的项目，并把真正阻塞项写入审计文件。禁止用“主要完成”“理论兼容”“应该可用”替代证据。

### 10. 工作纪律

- 直接执行审计、编辑、构建和验证，不要只给计划，也不要在审计完成后停下来等待普通确认。
- 每次开始先读审计文件的接力摘要和当前 diff；每次结束前必须更新审计文件，使下一模型无需聊天记录即可继续。
- 工作区是脏的也要与现有修改共存。禁止 `git reset --hard`、`git checkout --`、清理未知文件、回滚用户改动或用大范围机械重写覆盖并行工作。
- 不擅自提交、推送、改分支或改写历史，除非用户明确要求。可以读取其他 refs 和 `git show` 作为证据。
- 编辑范围紧贴当前审计项。发现无关问题先登记，不顺手大改。
- 不通过删除内容、改 ID、重置存档、要求玩家丢弃旧数据、强制新建世界或加入 Forge/NeoForge 运行库来完成迁移。
- 不把编译通过当成功，不把 warning 当作无条件可忽略，不把手工 smoke 当作所有领域的替代测试。
- 对外部下载、远端状态或缺少 fixture 保持可追溯性；记录来源和哈希，不执行不可信二进制中的任意脚本。
- 遇到阻塞时，先穷尽仓库、Git 历史、构建输出和隔离实验中的安全信息。只有确实需要用户提供旧存档、凭据或产品决策时才提问，同时继续推进不依赖该答案的任务。
