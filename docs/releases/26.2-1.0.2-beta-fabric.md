# The Aether for Minecraft 26.2 (Fabric beta 1.0.2)

This prerelease adds optional, public-API compatibility for Diggus Maximus 1.5.9-beta.1+26.2, Carry On 2.9.1, and WTHIT 20.0.0.

## Highlights

- Added Diggus Maximus API 1 data tags for the three Aether ore families and ordinary Aether mining tools. Ore families remain separate, while dungeon state-machine blocks, portals, block entities, dynamic blocks, accessories, weapons, armor, and special/AoE tools fail closed.
- Added Carry On API 1 relocation tags. Ordinary machines and containers such as the Altar, Freezer, and Incubator can be moved with their complete vanilla block-entity data, while dungeon structures, world-bound or dynamic blocks, hostile/transient entities, and unsafe stacking targets are denied.
- Added a WTHIT 20 common/client plugin using only the public `mcp.mobius.waila.api` surface. Ordinary players see trapped blocks and doorways as their safe facades and chest mimics as ordinary chests; creative and spectator players retain the true diagnostic view.
- Migrated the retained Jade integration to Jade 26.2.9's public Fabric API and custom entrypoint, then made Jade and WTHIT share one viewer-independent facade policy so their privacy behavior cannot drift. Both viewers preserve the non-sensitive “inventory contents have not been generated” hint for masked mimics.

## Compatibility safety

- All three integrations are optional. The Aether has no runtime dependency on Diggus Maximus or Carry On, and WTHIT classes are discovered only through WTHIT's plugin descriptor when WTHIT is installed.
- Diggus Maximus and Carry On integration is data-driven and uses Minecraft 26.2's singular registry tag paths with additive `replace: false` resources.
- Carry On uses its hard `c:relocation_not_supported` convention for unsafe blocks. No `CarryDataExtension` is registered because full vanilla block-entity serialization preserves the audited Aether machine state.
- WTHIT's server data provider makes the mimic decision from the authoritative server player and blocks item data for masked viewers; its client adapter never determines whether hidden inventory data may be sent.
- The release artifact does not bundle classes or JARs from Diggus Maximus, Carry On, WTHIT, or Jade.

## Validation

- Java 25 unit and GameTest coverage checks tag paths and contents, dependency ranges, optional class-loading boundaries, facade mappings, protected-block rejection, ore-family separation, one durability/drop settlement per actual excavation, Carry On block-entity save/reload and cancellation recovery, and dangerous entity/stack rejection.
- Direct API integration tests use the exact locally built Diggus Maximus 1.5.9-beta.1+26.2 and Carry On 2.9.1 worktrees without adding local paths or artifacts to the release build.
- Real client GameTests enter a singleplayer world with no viewer, Jade 26.2.9 alone, WTHIT 20.0.0 alone, and both viewers together. The Jade/WTHIT runs capture ordinary-player and creative-player mimic overlays and verify that both viewers load without contradictory or duplicate identity output. Dedicated-server startup is qualified with The Aether alone, each target mod separately, and all four mods together, including a second load of the same world.
- The GitHub release workflow performs a clean `test build` on Java 25, checks the packaged descriptors/tags and forbidden third-party/test packages, uploads the main and sources JARs, and appends their exact SHA-256 checksums below.

## Runtime

- Minecraft 26.2
- Fabric Loader 0.19.3
- Fabric API 0.153.0+26.2
- Java 25

## Known limits

- Static tags intentionally reject Aether objects whose safety depends on a dungeon, portal, multiblock, or dynamic world state instead of attempting to bypass those invariants with permissive callbacks.
- Automated client evidence covers the chest-mimic privacy boundary directly; trapped-block and doorway mappings are exercised through the shared registry-backed GameTest policy rather than pixel comparison for every block variant.
- This remains a beta prerelease. Multiplayer qualification with third-party configuration overrides and data packs is still recommended before adopting a large modpack as production-stable.

The release workflow appends the exact SHA-256 checksums produced by the remote build.
